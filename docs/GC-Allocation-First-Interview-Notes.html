GC Optimization Answer
Allocation → Measure → Flags

Dark · pen boxes · follow-ups · tables. Print or open offline and copy into your notebook.

1 · What you say first

Golden sentence:
“I first reduce allocation in code, then measure, and only then change the collector or flags.”
SAY THIS (full version)
I don’t start by flipping GC flags. First I look at whether the app creates too much garbage: unnecessary objects per request, string churn, big defensive copies, unbounded caches. Less allocation means less GC work — no matter which collector we use. Then I measure with GC logs and JFR to confirm pauses are actually the problem. Only after that do I tune G1 or consider switching to ZGC.

3 · Allocation tricks table (mention these)

Smell (what you see in code) What it does to GC What you say you’d do
New DTO / mapper objects on every request Young gen fills fast → frequent Young GC Avoid map→map→map chains; return leaner responses; reuse where safe
String concat in hot loops (+, String.format) Tons of short-lived String / StringBuilder garbage One StringBuilder; precompute; don’t format in tight paths
Copying large lists/arrays “just in case” Big short-lived objects → promote or humongous pressure Don’t materialize streams early; size collections upfront; avoid blind copies
Autoboxing (List<Integer>, boxed map values) Extra boxed objects on hot paths Prefer primitives in hot paths when it matters
Logging builds strings even when level is OFF Hidden allocation tax on every request isDebugEnabled / parameterized logging
Unbounded cache / static Map Objects never die → Old fills / “leak” TTL / max size; don’t cache request-scoped data forever
New byte[] / buffers per request High allocation rate + possible direct memory pressure Buffer pooling / reuse; watch direct memory limits
IF THEY ASK “give a concrete example”
A common one is building a big JSON DTO graph and copying collections at every service layer — or concatenating strings while building search filters inside a loop. Both can dominate Young GC even when heap size looks fine.

4 · Follow-ups — if they ask this → say that

FOLLOW-UP
How do you find high allocation in production?
→
ANSWER
JFR allocation profiling or async-profiler alloc mode, plus GC logs for allocation rate and pause time. If needed, compare two class histograms over time. Rank top allocating sites and fix the hottest ones first — don’t guess.
FOLLOW-UP
What if allocation is already low and pauses still hurt?
→
ANSWER
Trust the data: GC logs for pause vs SLO. For G1 check Full GC causes (humongous, to-space exhausted, late IHOP). Only then tune — or move to ZGC if p99 is GC-bound on Java 21+.
FOLLOW-UP
Won’t reducing allocation take longer than changing a flag?
→
ANSWER
A flag can buy time, but if the app allocates aggressively, GC cost returns under load. Fixing allocation is the durable fix; flags handle remaining collector trade-offs after the code is sane.
FOLLOW-UP
How do you know it’s GC and not something else?
→
ANSWER
Correlate p99 spikes with GC pause timestamps. If the GC log is clean, check safepoints, CPU throttling, and swap. Bad latency + clean GC logs is often not a collector problem.
FOLLOW-UP
What would you change first on a Spring Boot service in Kubernetes?
→
ANSWER
Baseline: MaxRAMPercentage, GC logging, HeapDumpOnOOM. Then allocation hotspots. Then G1 pause/IHOP only if logs justify it. ZGC only if measurement shows GC pauses break the SLO.
FOLLOW-UP
Why not just pick ZGC for everything?
→
ANSWER
ZGC costs more CPU and memory. I switch only when measurement proves GC pauses break latency SLO. For most services G1 is the right starting point after allocation is under control.

5 · Mini dialogue (practice out loud)

Interviewer: How would you optimize GC?
You: Reduce allocation first, measure, then tune collector/flags.
Interviewer: What does reduce allocation mean in practice?
You: Cut per-request object churn — DTOs, string concat, big copies, autoboxing, bad caching — then verify with JFR.
Interviewer: And if it’s still bad?
You: Confirm pauses with GC logs; for G1 inspect Full GC cause; if latency SLO is still GC-bound, evaluate ZGC and accept the CPU/memory cost.
