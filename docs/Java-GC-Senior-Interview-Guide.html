Top ROOTS → arrows down to A B C. Separate X↔Y with a big X. Write: “cycle without root = dead”.
Story — GC is an electrician, not a detective: It follows wires from roots. Lights that turn on are live. Two lamps wired only to each other (not to the wall) → dark → garbage.
Java memory leak: The object’s job is done — it should be garbage — but something still holds a reference.
Classic culprits:
  • static Map / unbounded cache (no eviction)
  • forgotten ThreadLocal (no remove)
  • unregistered listener / callback
PROBLEM
Heap baseline keeps rising (sawtooth bottom drifts up)
→
SOLUTION
Heap dump → MAT dominator tree → find retainer → usually static / ThreadLocal / listener

10 · GetYourGuide-style mock answers

Read these out loud. Then close the page and reproduce them without looking. Use the 4-box formula.

Q: How does GC work?

Objects live on the heap. GC walks from roots (stack, statics, JNI) and keeps the reachable set; unreachable objects are garbage. Generational collectors gather short-lived objects cheaply in Eden and promote long-lived ones to Old. Pauses (STW) affect user latency, so collector choice is a throughput-vs-latency trade-off. In production I look at allocation and leaks first, then measure, then tune.

Q: Which GC would you pick?

For a normal request/response service I start with G1 — pause-targeted and the default. For batch/throughput jobs I’d consider Parallel. If p99 SLO is broken by GC pauses and logs/JFR prove it, I’d try ZGC on Java 21+. I also watch for Serial GC on tiny pods.

Q: You’re seeing frequent Full GCs — what do you do?

In G1, Full GC is an alarm. I read the log cause: humongous → grow region / split the object; to-space exhausted → grow heap / reserve; late marking → lower IHOP / cut allocation. In parallel I check for a leak with a heap dump.

Q: How do you optimize GC?

1) Mechanism: G1 is region-based with Young + Mixed collections.
2) Trade-off: shorter pauses usually cost more CPU; ZGC also wants more memory.
3) Measurement: GC logs, JFR allocation, MAT if needed.
4) Decision: humongous → region; Old filling → IHOP/allocation; SLO → ZGC.
Always cut unnecessary allocation in code first.

Q: What is a memory leak in Java? How do you find it?

An object that should be unreachable still has a root path (static Map, ThreadLocal, listener). Symptom: heap baseline rising. Take a heap dump, open in MAT, use dominator tree / leak suspects, fix the retainer, verify with another dump or JFR allocation profiling.

Q: OOMKilled but no Java OOM — what’s going on?

The container killed the process for total RSS, not necessarily Java heap OOM. Heap is only part of JVM memory: metaspace, thread stacks, direct buffers also count. Leave headroom with MaxRAMPercentage, bound metaspace/direct if needed, inspect with NMT.
