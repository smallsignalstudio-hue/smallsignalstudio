PART A · JAVA — Core, Concurrency, Memory
Java thesis: Data structures, equality, concurrency, and memory are one story: where state lives, who can see it, and how you keep it correct under load.

A1 · HashMap — how it works & collisions

figure — HashMap bucket array + chain / tree
key.hashCode() → spread → index = (n-1) & hash
▼
table[] buckets
[0] empty
[1] → (K1,V1) → (K4,V4)

Draw array of boxes. Some empty. One box has a linked list of nodes. One box labeled TREE. Arrow from hash(key) into a bucket index.
Story — coat check: Hash = which rack. Collision = two coats land on the same rack number. You hang them in a chain. If the chain gets long (Java 8+: usually ≥8 and table large enough), the rack becomes a balanced tree so lookup stays fast.
StepWhat happens
1 Put / getCompute hash, map to bucket index.
2 CollisionSame bucket. Walk chain (or tree). Compare with equals.
3 ResizeWhen size > capacity × loadFactor (default 0.75), double table and redistribute.
4 TreeifyLong chains become red-black trees (Java 8+) to avoid O(n) worst case.
⚠ Trap: Mutating a key after insert (changing a field used in hashCode/equals) can make the entry unreachable in the map. ⚠ Trap: HashMap is not thread-safe. Concurrent put can corrupt structure. Use ConcurrentHashMap.
PROBLEM
HashMap looks up slow under adversarial or bad hashCodes
→
SOLUTION
Fix equals/hashCode quality; Java treeifies long buckets; never share HashMap across threads without sync
If they ask: “How does ConcurrentHashMap differ?”
CHM (ConcurrentHashMap) allows concurrent readers/writers with fine-grained locking / CAS (Compare-And-Swap) on bins. No null keys/values. Size is approximate under concurrency. Prefer it for shared mutable maps.
If they ask: “What is load factor?”
Default 0.75 balances space vs resize cost. Lower → fewer collisions, more memory. Higher → denser table, longer chains before resize.
notebook → Hash → bucket → equals. Collisions = chain, then tree. Resize at 0.75. Not thread-safe.

// Safe pattern (records do this for you)
@Override public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof User u)) return false;
  return Objects.equals(id, u.id);
}
@Override public int hashCode() { return Objects.hash(id); }
If they ask: “When do I use identity (==) vs equals?”
== compares references (or primitive values). equals compares logical value. For domain keys in maps/sets, always equals+hashCode. For enums, == is fine and preferred.
If they ask: “Can I use mutable fields in hashCode?”
Avoid. If a field changes after insert into a Hash-based collection, the object can vanish logically. Prefer immutable keys (id, records).
notebook → equals true ⇒ same hashCode. Same hash ⇏ equals. Break this → HashMap ghosts.

CompletableFuture: a promise of a result. Chain with thenApply (transform), thenCompose (flat async), thenCombine (wait two), exceptionally / handle (errors). Always pass an executor for blocking work. 
CompletableFuture<User> u = supplyAsync(this::loadUser, ioPool);

If they ask: “Why not use commonPool for HTTP (Hypertext Transfer Protocol)/DB (database)?”
commonPool is shared and sized for CPU (Central Processing Unit) parallelism. Blocking I/O (Input/Output) starves everyone using parallelStream/CF (CompletableFuture) defaults. Give I/O (Input/Output) its own bounded pool.
If they ask: “How do you size a pool?”
CPU (Central Processing Unit)-bound ≈ cores (+ small). I/O (Input/Output)-bound higher, but bounded by downstream capacity. Measure queue latency and rejections; never unbounded growth.
notebook → Bound the queue. Name threads. Don’t block commonPool. CF (CompletableFuture) needs an executor for I/O (Input/Output).

If they ask: “How do you optimize GC (Garbage Collection)?”

AdvantageWhy it matters in production

B2 · @Transactional — how it works & surprises

figure — proxy wraps the bean
Caller→ Spring Proxy→ begin TX (transaction)→ target method→ commit/rollback
Caller hits PROXY first, not the raw object. TX (transaction) boundary = proxy boundary.
⚠ Self-invocation trap: this.otherTransactional() bypasses the proxy → no new transaction / no advice.
⚠ Rollback default: rolls back on unchecked exceptions; checked exceptions do not roll back unless configured.
⚠ readOnly is a hint to the flush mode / routing — not a hard DB (database) guarantee alone.
SurpriseWhat to say / fix
Self-invocationMove method to another bean, or use AspectJ weaving. Don’t call this.
Checked exception swallowedrollbackFor = Exception.class when needed.
Long TX (transaction) holding DB (database) connectionsKeep TX (transaction) short; don’t call HTTP (Hypertext Transfer Protocol) inside a transaction.
REQUIRES_NEW (always start a new independent transaction)Suspends outer TX (transaction); useful for audit logs; easy to misuse.
LazyInitializationExceptionSession closed after TX (transaction); fetch join / DTO (Data Transfer Object) projection / OpenSessionInView (keep Hibernate session open during view rendering) carefully (often avoid OSIV (Open Session In View)).
If they ask: “Where do you put @Transactional?”
On the service layer that defines the use-case boundary. Not on controllers. Repositories may be transactional by default in Spring Data, but business atomicity belongs in services.
If they ask: “Propagation REQUIRED vs REQUIRES_NEW (always start a new independent transaction)?”
REQUIRED joins existing or creates one — default. REQUIRES_NEW (always start a new independent transaction) always starts independent TX (transaction); outer rollback won’t undo the inner work.
notebook → TX (transaction) = proxy. No self-call. Short TX (transaction). Rollback on RuntimeException by default.

B5 · Blocking vs non-blocking I/O (Input/Output)

figure — thread waits vs callback continues
BLOCKING
Thread calls DB (database) → sleeps until bytes return → holds a worker the whole time
NON-BLOCKING
Thread registers interest → returns to do other work → continuation runs when ready
Left: stick figure asleep on chair labeled DB (database). Right: stick figure juggling many sockets.
Meaning: Blocking I/O (Input/Output) occupies a thread for the wait duration. Non-blocking I/O (Input/Output) frees the thread during the wait. Throughput gains appear when waits dominate and the platform supports async drivers end-to-end.
If they ask: “Is async always faster?”
No. For CPU (Central Processing Unit)-bound work or low concurrency, blocking is simpler and often fine. Async wins when you multiplex many slow I/O (Input/Output) waits on few threads — and you pay complexity.
notebook → Blocking holds threads while waiting. Non-blocking frees them. Complexity cost is real.

B7 · Circuit breaker · retry · timeout — together

figure — defense layers around a call
timeout→ retry (bounded)→ circuit breaker→ dependency
Concentric shields. Timeout innermost on the call. Retry only for safe/idempotent. Breaker opens on error rate.
ToolJobRules
TimeoutBound wait timeAlways set; align with SLO (Service Level Objective) budget.
RetryAbsorb transient faultsOnly idempotent ops; exponential backoff + jitter; cap attempts.
Circuit breakerStop calling a sick dependencyOpen → fail fast / fallback; half-open probe; prevent retry storms.
BulkheadIsolate poolsOne slow dependency mustn’t exhaust all threads.
⚠ Retry without timeout amplifies load. Retry on non-idempotent POST can double-charge. Breaker without bulkhead still shares the same exhausted pool.
If they ask: “Order of policies?”
Timeout per attempt. Limited retries with backoff for idempotent calls. Circuit breaker around the dependency. Bulkhead isolation for thread/connection pools. Fallbacks only when business allows degraded mode.
notebook → Timeout always. Retry only if idempotent. Breaker stops stampedes. Bulkhead isolates.

C2 · Composite indexes — help and harm

figure — phone book ordered by (last, first)
INDEX (status, created_at)
✔ WHERE status=? AND created_at>?
✔ WHERE status=? ORDER BY created_at
✖ WHERE created_at=? alone (leftmost prefix missing)
Write columns left→right. Queries must use a left prefix of the index.
HelpsHurts / wastes
Equality/range matching leftmost columns; covering indexes; ORDER BY aligned with index Low-selectivity leading column; write amplification; unused indexes; functions on column that prevent index use
Leftmost prefix rule: Index (a,b,c) helps (a), (a,b), (a,b,c). It does not help (b) or (c) alone.
If they ask: “When is an index harmful?”
Every write updates indexes. Too many indexes slow inserts/updates, bloat storage, and confuse the planner. Drop unused ones. Also wrong indexes can make the planner pick a bad nested loop.
notebook → Composite = leftmost prefix. Indexes speed reads, tax writes. Measure with EXPLAIN.

C4 · Optimistic vs pessimistic locking

OPTIMISTIC

version column / ETag

UPDATE … SET ver=ver+1 WHERE id=? AND ver=?
0 rows → conflict → retry/fail

Best when conflicts are rare

PESSIMISTIC

SELECT … FOR UPDATE

Lock row now
Others wait / fail

Best when conflicts are common or stakes high

If they ask: “Booking seats — which lock?”
Hot inventory often needs pessimistic locks or atomic single-row updates / capacity counters. Optimistic works if contention is low. For Ticketmaster-style hot events, design holds with TTL (Time To Live) + atomic reservation, not last-write-wins.
notebook → Optimistic = version check. Pessimistic = lock now. Pick by conflict rate + cost of being wrong.

DEEP FOLLOW-UPS — what seniors get asked next

Java deep

If they ask: “HashMap resize is O(n) — is that a problem?”
Amortized, yes occasional spikes. Pre-size with expected capacity if you know it. Under concurrency use ConcurrentHashMap which resizes more scalably. Avoid pathological key distributions.
If they ask: “Why ConcurrentHashMap disallows null?”
Ambiguity: null return from get could mean ‘missing’ or ‘stored null’, and nulls complicate concurrent presence checks. Design with Optional at API (Application Programming Interface) edges, not null map values.
If they ask: “fail-fast iterators?”
ArrayList iterators detect structural modification via modCount and throw ConcurrentModificationException. It’s best-effort against bugs, not a concurrency strategy — don’t rely on it for thread safety.
If they ask: “virtual threads (Java 21) vs pools?”
Virtual threads shine for high-concurrency blocking I/O (Input/Output) — many waiting tasks without burning OS threads. Still bound carrier threads and downstream pools (DB (database)). Don’t pin with long synchronized / native calls. Platform thread pools still matter for CPU (Central Processing Unit) work.
If they ask: “CompletableFuture vs reactive WebFlux?”
CF (CompletableFuture) is fine for a handful of parallel fan-outs in MVC (Model-View-Controller). WebFlux/reactive is a whole stack commitment for end-to-end non-blocking. I don’t sprinkle CF (CompletableFuture) as a fake reactive architecture.
If they ask: “How do you publish an immutable object safely?”
Initialize via constructor, assign to a volatile field or publish under a lock / final field freeze (safe publication). Improper publication can let another thread see default field values.

Spring deep

If they ask: “What does @Transactional(readOnly=true) actually do?”
Hint for flush mode and some connection routing (read replicas). It does not magically make the database reject writes. Still avoid accidental dirty flushes; use it to signal intent and reduce flush cost.
If they ask: “Open Session in View?”
Keeps the Hibernate session open during view rendering so lazy loads work — and hides N+1 (one query for parent + one query per child row) into the web layer, holding DB (database) connections longer. I prefer explicit fetch plans/DTOs and OSIV (Open Session In View) off in APIs (Application Programming Interfaces).
If they ask: “How do you test @Transactional rollback?”
Integration test: invoke service that throws, assert DB (database) unchanged. Or use @Transactional on the test with controlled rollback. Verify proxy is applied — calling via bean, not this.
If they ask: “Bean scopes?”
Singleton default. Prototype = new instance each injection. Request/session for web-scoped state. Injecting narrower scope into singleton needs providers/object factories — classic gotcha.
If they ask: “Saga choreography vs orchestration?”
Choreography: services react to events — loose, harder to see the flow. Orchestration: a coordinator drives steps — clearer control/compensation, extra component. Pick based on complexity and observability needs.

Data & API (Application Programming Interface) deep

If they ask: “Covering index?”
An index that contains all columns needed by the query so the engine avoids heap/table lookups. Great for hot read paths; costs write/storage.
If they ask: “Write skew?”
Two transactions read overlapping state, each writes a different row, both commit, breaking a multi-row invariant. Snapshot isolation can allow it. Fix with SERIALIZABLE, SELECT FOR UPDATE, or a constraint/aggregate lock.
If they ask: “Exactly-once in messaging?”
True exactly-once across systems is hard. Practically: at-least-once delivery + idempotent consumers + dedupe keys / outbox. That’s the production pattern.
If they ask: “401 vs 403 vs 404 for authz?”
401 when no/invalid credentials. 403 when identity is known but not permitted. Sometimes 404 to avoid leaking existence of a resource — product/security choice; be consistent.
If they ask: “How do you version APIs (Application Programming Interfaces)?”
Prefer additive changes. If breaking: URI (Uniform Resource Identifier) version (/v2) or header version with a sunset policy. Never silently change meaning of fields. Contract tests catch accidental breaks.
If they ask: “Cache-aside race?”
Writer updates DB (database) and deletes cache; concurrent reader can refill cache with old DB (database) read. Mitigate with versioned values, short TTL (Time To Live), or transactional outbox-driven invalidation ordering carefully.

Ops deep

If they ask: “SLI (Service Level Indicator) / SLO (Service Level Objective) / SLA (Service Level Agreement) / error budget?”
SLI (Service Level Indicator) = measured indicator (availability, latency). SLO (Service Level Objective) = target on that indicator. Error budget = allowed failure. SLA (Service Level Agreement) = external contractual promise. Burn error budget → slow feature work, fix reliability.
If they ask: “How do you make canaries trustworthy?”
Compare canary vs control on the same metrics, enough traffic, same dimensions. Auto-abort on SLO (Service Level Objective) burn. Avoid declaring success on five minutes of lucky traffic.
If they ask: “Blue/green vs canary vs rolling?”
Rolling replaces pods gradually. Canary sends a small % to new version with metrics gate. Blue/green switches traffic between two full environments — fast rollback, more cost. I pick based on risk and infra cost.
If they ask: “What goes in a postmortem?”
Timeline, user impact, root cause, detection gaps, what worked, action items with owners — blameless. Focus on system fixes (tests, alerts, runbooks), not heroes.
notebook → Follow-ups reward precision: name the trap, the metric, and the mitigation.
MOCK DIALOGUE — 90 seconds of senior signal

Interviewer: “Walk me through how you’d keep a booking API (Application Programming Interface) correct and fast.”

I’d separate read and write paths. Reads: indexed queries, cursor pagination, cache with invalidate-on-write for hot event pages. Writes/booking: short DB (database) transaction with atomic seat/inventory decrement or hold row + TTL (Time To Live); idempotency key on POST to make client retries safe. Cross-service payment: local TX (transaction) + outbox event, saga compensation if charge fails — not 2PC (Two-Phase Commit). Resilience: timeouts and breaker to payment; no retry that can double-charge without idempotency. Prove with integration tests around the reservation invariant, and watch p95 (95th percentile) + 5xx on the book endpoint in canary.

Interviewer: “You see intermittent ConcurrentModificationException and lost counter updates.”

CME (ConcurrentModificationException) on a shared ArrayList means concurrent structural modification — replace with a concurrent structure or confine to one thread. Lost counters sound like unsynchronized i++ — switch to AtomicLong or LongAdder, or synchronize the critical section. I’d reproduce under load, confirm with jstack/JFR (Java Flight Recorder), then add a test that fails on the race before fixing.

Interviewer: “Our Spring service commits even when we throw a checked exception.”

Default @Transactional rolls back on unchecked exceptions only. I’d set rollbackFor appropriately or wrap in a runtime exception at the boundary. Also I’d verify we’re not self-invoking and that the exception isn’t swallowed before leaving the proxy.
SPOKEN ANSWER BANK — rapid fire

Read out loud. Then close the page and reproduce. Each answer is Mechanism → Trade-off → Measurement → Decision when relevant.

Q: How does HashMap handle collisions?

It hashes the key to a bucket. Colliding entries form a linked list in that bucket; in Java 8+, long chains treeify into a red-black tree so lookup stays logarithmic. Equality is decided with equals. Resizing at load factor 0.75 redistributes entries. HashMap itself isn’t thread-safe — ConcurrentHashMap for shared mutation.

Q: What’s the equals/hashCode contract?

If two objects are equal, they must have the same hashCode. The reverse is not required. Break this and HashMap/HashSet lose entries. Keep keys immutable; generate both methods from the same fields — records help.

Q: ArrayList or LinkedList?

ArrayList by default: O(1) random access and cache-friendly arrays. LinkedList rarely wins in real services because of pointer chasing. For queues I use ArrayDeque.

Q: When do you use Optional and Streams?

Streams for clear transform/filter/collect pipelines; avoid forced cleverness and blind parallelStream. Optional as a return type for absence; not for fields/parameters; prefer orElseGet for expensive defaults.

Q: synchronized vs volatile vs AtomicInteger?

synchronized for mutual exclusion around invariants. volatile for visibility of flags/references, not for atomic compound updates. AtomicInteger for lock-free counters/CAS (Compare-And-Swap). volatile i++ is still racy.

Q: How do thread pools and CompletableFuture work together?

A pool queues tasks onto worker threads with bounds and a rejection policy. CompletableFuture chains async steps; I pass an explicit executor for blocking I/O (Input/Output) so I don’t starve the commonPool. Timeouts and exception handling belong in the chain.

Q: How does Java memory / GC (Garbage Collection) work?

Stack holds per-thread frames and references; heap holds objects; GC (Garbage Collection) reclaims unreachable heap objects from roots. Generational collectors clear short-lived objects cheaply. I manage pauses and leaks with measurement — allocation and retainers first, then flags. Full guide in the GC (Garbage Collection) document.

Q: Why immutability?

Immutable objects are safe to share without locks, make hash keys stable, and reduce temporal bugs. I use final fields/records and copy-on-write style updates.

Q: How does Spring DI (Dependency Injection) work?

The container creates beans and injects dependencies — constructor injection preferred for required deps and testability. Singletons are shared, so keep them stateless or synchronize carefully.

Q: @Transactional pitfalls?

Advice runs through a Spring proxy, so self-invocation skips the transaction. Default rollback is for runtime exceptions. Keep transactions short and outside remote calls. Watch LazyInitializationException after the session closes.

Q: MVC (Model-View-Controller) vs WebFlux?

MVC (Model-View-Controller) is thread-per-request and fits blocking JDBC (Java Database Connectivity). WebFlux is event-loop reactive and needs non-blocking I/O (Input/Output) end-to-end. I don’t migrate for fashion — only when concurrency measurements demand it and the stack can be async.

Q: Distributed transactions?

I avoid 2PC (Two-Phase Commit) across microservices. Local ACID (Atomicity, Consistency, Isolation, Durability) + outbox for reliable events + saga compensations + idempotent consumers. Design service boundaries so most writes don’t need cross-service atomicity.

Q: Circuit breaker, retry, timeout together?

Timeout every call. Retry only idempotent operations with backoff and jitter. Circuit breaker fails fast when a dependency is sick. Bulkheads isolate pools so one dependency can’t take the whole process down.

Q: Isolation levels / anomalies?

Dirty read sees uncommitted data; non-repeatable sees changed rows; phantom sees new rows. Higher isolation reduces anomalies but increases conflicts. Know your database defaults — Postgres RC (Read Committed) vs RR (Repeatable Read)/snapshot behavior.

Q: Optimistic vs pessimistic locking?

Optimistic uses a version check and retries on conflict — good when conflicts are rare. Pessimistic locks rows up front — good for hot contended updates. Booking inventory often needs atomic reserves, not blind last-write-wins.

Q: How do you chase a slow endpoint?

Metrics → distributed trace to find the slow span → check N+1 (one query for parent + one query per child row) and pool waits → EXPLAIN ANALYZE for SQL (Structured Query Language) → fix → verify p95 (95th percentile) against baseline. Don’t guess indexes without a plan.

Q: Readiness vs liveness?

Readiness controls traffic membership; liveness restarts a stuck process. Never make liveness depend on an external DB (database) or you’ll restart the world during a dependency blip.

Q: 5xx spike — what do you do?

Confirm blast radius, check whether a deploy lines up, mitigate first — rollback or flag off if correlated — then diagnose with logs and traces. One change at a time. Postmortem after service is stable.

Q: P95 (95th percentile)/P99 (99th percentile)?

They describe the tail: 5% or 1% of requests are slower than that number. Users feel tails; averages hide them. SLOs should track percentiles and error budget burn.

Q: When do you rollback?

If user impact is material and the cause isn’t quickly clear, rollback or disable the flag to restore service. Investigate on the healthy version. Irreversible migrations are a process smell — use expand/contract.
